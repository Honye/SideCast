## 更新日志

### 2026-11-23 · M2 分应用音频捕获与本地路由
- **应用识别（FR-ROUTE-01/09）**：读取 Core Audio 的进程列表，把辅助进程归到所属应用（例如浏览器的各个辅助进程算作同一个浏览器）。只列出正在发声或设置过规则的应用。
- **分应用路由（FR-ROUTE-02/04）**：每个应用可选「系统默认 / 任一本机输出设备 / 已连接的接收端」。实现方式：给应用建 Process Tap（捕获其声音并让原输出静音），再把发往同一目的地的应用放进一个私有聚合设备里混音输出。切换即时生效，无需重启应用。
- **分应用音量与静音（FR-VOL-01~04）**：0–100% + 静音，带平滑过渡避免爆音；对本机设备同样生效。
- **默认与离线（FR-ROUTE-06/07）**：没设过规则的应用完全不经过 SideCast；目标设备离线时该应用静音等待，界面显示「设备离线」，设备回来自动恢复。
- **持久化（FR-ROUTE-08）**：规则按应用保存，重启 SideCast 后自动恢复（已实测）。
- **安全退出（PRD 7.2）**：Tap 使用「读取时才静音」模式，SideCast 退出或崩溃后各应用自动恢复正常发声。
- **设置窗口**：改为自管理窗口，打开时显示 Dock 图标、关闭后隐藏（PRD 6.8）；再次打开 SideCast 时会弹出设置窗口。目前有「Apps」「Devices」两个页面（临时版，M4 完善）。
- **实测**（本机）：播放 440 Hz 测试音，设为 50% 音量后捕获到的电平与理论值一致（0.015）；改到不存在的设备时显示离线并静音；恢复默认后 Tap 被移除；重启后规则恢复。14 个单元测试通过。
- **尚未用耳朵验证**：我无法听到声音，实际听感（音量变化、切到其他输出设备、有无杂音）需要你试一下，见下方「需要你操作的事项」。

### 2026-11-23 · M1 设备连接与配对
- **设备身份**：每台设备有固定的设备 ID 和 Ed25519 身份密钥（存钥匙串）。
- **加密握手**：X25519 密钥交换 + 双方用身份密钥签名；之后控制通道全部用 ChaCha20-Poly1305 加密，带计数器防重放。同时派生出音频加密密钥，供 M3 使用。
- **配对码（FR-CONN-06）**：任一方不信任对方时，Mac 弹出浮动窗口显示 6 位数字码（2 分钟有效），接收端输入；双方用与本次握手绑定的 HMAC 互相证明，成功后保存信任。输错或超时都会断开，需重新发起。
- **发现与连接（FR-CONN-01/02/08）**：Bonjour `_sidecast._tcp`，开启点对点 Wi-Fi；Mac 和接收端都能发起连接。
- **占用（FR-CONN-10）**：接收端已连着一台 Mac 时，拒绝其他 Mac 并提示「正在被 xxx 使用」。
- **断线重连（FR-CONN-11）**：Mac 对用户想连的接收端，断线后 2 秒自动重试，对方重新出现时也会重试。
- **界面（临时版）**：Mac 菜单栏里列出附近接收端（连接/断开/状态）；iPad 上列出附近 Mac、配对码输入框、已连接页面。完整界面在 M4。
- **测试**：12 个单元测试通过。在本机 Mac + iPad 模拟器（iOS 27.0）上实测：发现 → 输入配对码 → 已连接 → 断开 → 重连免配对码，全部正常。
- 各平台最低版本由 27.2 调为 **27.0**（仍在 27.x 内）：本机模拟器只有 27.0，你的设备是 27.0.1，按 27.2 打的包装不上。

## 技术决策记录

| 决策 | 原因 |
|---|---|
| 单一多平台 target，用 `#if os(macOS)` 区分发送端/接收端 | 共用协议与加密代码；PRD 要求 Mac 接收模式与发送端是同一个 App |
| 官网版也保持 App 沙盒 | 同一份代码后续可直接上 Mac App Store；系统级虚拟音频设备（V1）再以独立驱动安装 |
| 控制通道走 TCP，音频（M3）走单独的 UDP | 控制消息要求可靠有序；音频要低延迟，丢包不重传 |
| Mac 上身份密钥存在登录钥匙串（不是数据保护钥匙串） | 后者需要描述文件授权，开发签名下不可用 |
| 断线后由 Mac 负责自动重连，接收端不主动重连 | 避免两端同时重连互相冲突 |
| 每个应用一个 Process Tap；同一目的地的应用共用一个私有聚合设备，在实时线程里混音 | 改音量只改增益不重建；改目的地只重建受影响的聚合设备 |
| 判断辅助进程属于哪个应用时，优先用系统的「负责进程」接口（非公开，运行时查找），找不到再沿父进程查 | 浏览器、WebKit 等的音频进程大多不是应用本身 |

## 已知问题 / 风险

| 问题 | 影响 | 计划 |
|---|---|---|
| 配对码校验用的是「HMAC + 6 位码」，没有使用 PAKE（如 SPAKE2）。若攻击者在配对那一刻实施中间人攻击，可离线穷举 6 位码 | 仅影响首次配对那几十秒、且需攻击者在同一网络主动劫持连接 | 后续换成 PAKE 协议；CryptoKit 没有现成的公开 PAKE 接口，需要自行实现或引入库 |
| 同 Apple ID 自动信任（FR-CONN-05）尚未实现，目前同账号设备也要输配对码 | 首次连接多一步 | M6 实现，需开启 iCloud 能力 |
| 「负责进程」接口不是公开 API | Mac App Store 审核可能不通过 | 官网版先用；上架 App Store 版前评估替代方案（只用父进程关系） |
| 从终端运行的命令行程序（如 afplay）会被归到启动它的应用下（例如终端） | 显示名可能不直观 | 符合系统的归属关系，暂不处理 |
